# Задача 1.28: ПВЗ Яндекса пропадают при заказе со сохранённым адресом

**Задача:** 1.28-saved-address-pvz
**Дата:** 2026-11-19
**Статус:** в работе

## Цель

Разобраться в обращении клиента: при повторном заказе из личного кабинета с ранее
сохранённым адресом из списка методов доставки пропадают ПВЗ Яндекса; при выборе
«Новый адрес» и вводе тех же полей руками — ПВЗ появляются. Воспроизвести сценарий
«один и тот же адрес: сначала из сохранённых, затем введённый заново», дать диагноз:
баг / данные / задумано. Если всё нормально — закрыть тему с объяснением.

## Область

- Витрина dev (`eridanus.dev.modulecode.ru`), чекаут Simple, блок адреса доставки
  (выбор сохранённого адреса vs «Новый адрес»).
- Расчёт доставки ApiShip (`system/library/apiship/apiship.php`), кеш калькулятора (1.27).
- Данные `oc_address` (city / zone_id / postcode) тестового и реального клиентов.

## Не входит

- Изменения настроек/кода до постановки диагноза (сначала reproduцировать и объяснить).

## Контекст из прошлых задач

- 1.25 сессия-2: зона «Ленинградская область» убирает самовывоз Яндекса при любом городе,
  зона «Санкт-Петербург» даёт все 3 метода — регион доминирует над городом.
- 1.25 HAR: у заказчика под своим логином (сохранённый адрес address_id=67, зона 102→106)
  Яндекс ПВЗ отсутствовали; тогда объяснили кешем корзины (Единорог).
- 1.27: кеш калькулятора — пустой ответ не кешируется, асимметричный TTL 120с, полный 300с;
  хэш включает страну+регион+город+индекс+адрес+корзину.

## Критерии приёмки

1. Сценарий клиента воспроизведён (или добросовестно не воспроизведён) на dev с фиксацией
   POST-запросов и ответов калькулятора (tracing-ID).
2. Дан ответ: точная причина различия методов между сохранённым и введённым адресом.
3. Клиенту подготовлен понятный ответ (или фикс, если это баг кода).

## Ограничения

- Реальные данные клиентов не изменять (база — копия боевой); чтение — можно.
- Перед какими-либо правками БД/настроек — бекап и подтверждение пользователя.
