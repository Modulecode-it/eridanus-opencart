# Спека 2.1 — Этап 2: UX оформления заказа (регион на шаге адреса + адрес в способе доставки) и дизайн по ТЗ

Дата: 2026-10-12. Статус: в работе (требования собраны; реализация после 1.19/1.21).

## Решения и требования заказчика

1. **Регион: вариант (б)** (подтверждён 2026-10-12): выбор региона/города из корзины
   убирается; город спрашивается один раз — на шаге адреса, с автодополнением.
2. **Объединение блоков** (пожелание из письма 2026-10-12): шаг «Адрес доставки»
   перенести в блок способа доставки — внутри варианта «Курьер Яндекс.Доставки»
   выбор: «по ранее указанному адресу» / «по новому адресу».
3. Устранить дублирование полей (регион спрашивался и «в корзине», и в оформлении —
   наблюдение заказчика относится к аварийному штатному чекауту, см. 1.19; после
   восстановления Simple проверить, остаётся ли дубль в рабочем флоу).
4. Дизайн оформления — к скриншотам из ТЗ (материал ТЗ у Максима/заказчика).

## Контекст реализации

- Чекаут — Simple 4.11.9, шаблон одной колонки (1.13), блоки Покупатель → Адрес
  доставки → Доставка и оплата → Комментарий; настройки в `simple_settings`
  (oc_setting), API-settings по STACK.md, бэкапы 1.13/1.17.
- Гостевой заказ в Simple отключён (гостей редиректит на /login) — флоу гостей
  уточнить с заказчиком (в штатном чекауте гость проходил).
- Поля адреса для ПВЗ-методов уже минимизированы (`apiship.point*|` без Индекса/Адреса).
- Автодополнение города: кандидат — справочник ApiShip/Яндекс (используется картой ПВЗ),
  отдельный анализ источников (подгрузка списка городов в JS vs API-подсказки).

## Открытые вопросы

- «Ранее указанный адрес» для гостей не существует (нет профиля) — опция только
  для залогиненных? Какой флоу для гостей остаётся?
- Совместимость с расчётом котировок ApiShip (город нужен ДО выбора способа доставки
  для расчёта тарифов — при переносе адреса в метод курьера порядок расчёта меняется:
  город по-прежнему нужен раньше, возможно останется только поле «Город» на верхнем
  уровне, а полный адрес — внутри курьера).
- Влияет ли на наложку/предоплату порядок шагов (правило «нал только ПВЗ», 1.14).

## План

1. Восстановить Simple (1.19), зафиксировать текущий флоу скриншотами.
2. Анализ simple_settings: какие блоки/поля двигаются, что с валидацией ПВЗ.
3. Прототип изменений (настройки + при необходимости правки шаблонов Simple),
   приёмка Максимом → письмо заказчику на согласование перед реализацией на проде.
4. Дизайн-этап по скриншотам ТЗ (после функциональной части).
