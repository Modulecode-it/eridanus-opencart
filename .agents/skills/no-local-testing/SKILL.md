# No local testing — среда запуска на сервере

Проект (OpenCart 3.0.3.2) развёрнут **на сервере**. Локально нет ни рабочей среды
запуска сайта, ни БД, ни веб-сервера. Запрет касается **только PHP-приложения и
серверной архитектуры** (OpenCart, MySQL/MariaDB, веб-сервер). Всё, что не требует
этой среды, проверять локально можно и нужно.

## НЕ делай локально — PHP и серверная архитектура

- `php -S` и любые попытки «поднять OpenCart» локально
- `mysql` / `mariadb` / поднятие БД
- Веб-сервер (Apache/Nginx) и обращения к нему
- HTTP/браузерные запросы к витрине и домену проекта — это уже отдельное правило
  проекта (см. `STACK.md`, «Деплой На Сервер»: проверка сайта только через git-коммиты
  и серверный deploy)
- Любые попытки «проверить на ходу» запуском приложения локально

## Что МОЖНО локально — статические проверки

Если проверка **не запускает** PHP/БД/веб-сервер и не зависит от окружения OpenCart,
её можно выполнять локально:

- `php -l <file>` — если PHP установлен локально как бинарник (проверь заранее;
  на текущей машине PHP отсутствует — `php -v` не работает, тогда пропусти этот
  пункт). Это чистый lint синтаксиса, приложение не запускается.
- `bash -n script.sh` — синтаксис bash-скриптов.
- Валидаторы JSON/XML (в т.ч. проверка синтаксиса `.ocmod.xml` разбором текста), YAML.
- Twig-шаблоны — разбор текстом (структура, переменные, ссылки), без рендера.
- AST-утилиты проекта — в первую очередь `graphify update .` / `graphify query ...`
  (Python, работает локально без API-цены).
- Проверка регулярных выражений, форматов конфигов, имён/структуры файлов,
  целостности ссылок в документации.
- Чтение кода, разбор маршрутов/контроллеров/моделей OpenCart как замена запуску.

Эти проверки не заменяют runtime-тесты PHP/БД/витрины — они лишь подтверждают корректность
слоя, который **не относится к серверной архитектуре**.

## Что делаешь вместо runtime-проверок PHP/сервера

- Правишь код по задаче и описываешь пользователю, **что и где** изменилось.
- Для runtime-проверок (PHP/БД/витрина/админка) говоришь, что это нужно сделать на сервере
  (пользователь тестит там). Можно коротко подсказать шаги, которые имеет смысл выполнить
  на сервере (например: после деплоя обновить OCMOD-модификаторы в админке
  Extensions → Modifications → Refresh и очистить релевантный cache), но **не выполнять**
  их самому.
- Статические проверки выполняешь локально и явно отмечаешь в отчёте, что именно
  прогналось (например: «проверил XML-синтаксис `system/tweak.ocmod.xml`»,
  «прогнал `graphify update .`»).

## Если пользователь явно просит «запусти локально» PHP/сервер

Уточни, что локальной среды запуска в этом проекте нет, и предложи варианты:
тест на сервере, либо статический разбор кода здесь (см. выше). Не пытайся
«всё-таки» поставить PHP/БД/веб-сервер — это не требуется.
