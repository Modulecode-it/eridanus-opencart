# 1.24 — Фикс: «Warning: You do not have permission to access the API!» при редактировании заказа в админке

Дата: 2026-10-28. Операционный фикс (настройки в админке dev), изменений кода нет — specs/analysis не создавались.

## Симптом

Админка → Продажи → Заказы → кнопка «Редактировать» (любой заказ): на форме сразу всплывает `Warning: You do not have permission to access the API!`, состав заказа/методы оплаты/доставки не подтягиваются.

## Механика (диагноз)

1. Форма заказа (`admin/view/template/sale/order_form.twig`) шлёт AJAX **напрямую из браузера** в каталог: `{{ catalog }}index.php?route=api/...&api_token=...` (catalog из `HTTP(S)_CATALOG`).
2. `catalog/controller/startup/session.php` (строка 8) пускает сессию API только при тройном совпадении: `api.status='1'` × `api_session.session_id=token` × `api_ip.ip = REMOTE_ADDR` (JOIN). Любой промах → сессия не стартует → во всех `catalog/controller/api/*` нет `session->data['api_id']` → каждый возвращает `error_permission` («Warning: You do not have permission to access the API!», языковые ключи `catalog/language/*/api/*.php`).
3. При этом админ выдаёт токен, не проверяя статус API-пользователя: `ModelUserApi::getApi()` (`admin/model/user/api.php`) фильтра по `status` не имеет — поэтому токен в форме непустой и вводит в заблуждение.
4. На dev сайт стоит за reverse-proxy в Docker: PHP видит `REMOTE_ADDR = 172.18.0.2` (IP прокси-контейнера), реальный клиентский IP — только в `X-Forwarded-For` (проверено через `phpinfo.php`). Клиентский IP механизмом не учитывается.

Блокировали два фактора (оба из копии прод-БД):
- API-пользователь «Default» (api_id=1) был **Отключено** (status=0) — catalog требует status='1';
- в белом списке `api_ip` не было текущего IP прокси `172.18.0.2` (в списке ~97 прод-IP + Docker-IP `172.18.0.10`/`172.18.0.15` от прошлых попыток — IP прокси-контейнера дрейфует при пересоздании стека).

## Фикс (2026-10-28, через админку dev)

System → Users → API → «Default» → Edit:
- Status → **Включено**;
- вкладка «IP адрес» → добавлен `172.18.0.2` (подсказка текущего REMOTE_ADDR напечатана прямо на этой вкладке: «Ваш IP - …»);
- Save. Форма пересоздаёт список `api_ip` целиком (DELETE+INSERT в `ModelUserApi::editApi`) — старые ~97 IP сохранены как были.

## Верификация

- Форма `sale/order/edit&order_id=6729` (тест-заказ): warning исчез, вкладка «2. Товары» загрузила состав заказа через `api/cart/products` — API-сессия работает, а не просто «нет ошибки».
- Список API: Default → Включено, date_modified 28.10.2026.

## Наблюдения / риски

- **Дрейф Docker-IP**: если прокси-контейнер пересоздадут и он получит другой адрес — ошибка вернётся. Лечение за минуту: на вкладке «IP адрес» читаем подсказку «Ваш IP - …» и добавляем новый. (Прецеденты дрейфа: 172.18.0.10, 172.18.0.15.)
- **IP-белый-список за прокси вырождается**: `REMOTE_ADDR` у всех посетителей одинаковый (прокси), поэтому реальная защита API — api_token/ключ, а не список IP.
- **Прод**: в dev-копии базы API-пользователь был отключён с 01.09.2025 — если на проде он до сих пор выключен, редактирование заказов в админке прода падает с той же ошибкой (status='1' обязателен независимо от IP). При деплое/разборе прода проверить: System → Users → API → статус и IP.
- Токен API-ключа из карточки «Default» — секрет (копия прод-ключа), в документы не выносился.
