# Анализ 1.23 — Живые замеры и улики (2026-10-15)

## 1. Мёртвая валидация ПВЗ

- Тень `system/storage/modification/catalog/controller/checkout/simplecheckout_shipping.php`
  содержит патч `validator()`: `apiship` + `error` в коде метода → «Пожалуйста,
  выберите ПВЗ!». Контроллерная подмена неактивна (1.18) ⇒ никогда не исполнялась
  (подтверждение гипотезы-хвоста 1.18). Тень битая синтаксически: проверка вставлена
  в список параметров функции — если бы подмена работала, был бы PHP-fatal.
- Тень `.../checkout/shipping_method.php` (штатный чекаут): проброс `'script'` в
  method_data + та же проверка в `save()` ПОСЛЕ записи метода в сессию. Штатный
  чекаут — фолбэк (как в инцидент 1.19), патч перенесён с улучшением: проверка
  ДО записи в сессию.
- Механика ApiShip: без пункта тарифы ПВЗ отдаются с ключом
  `point_<provider>_<tariff>_error_<pickup>` (модель, строки ~316), `parce_code()`
  различает `point`/`door` delivery_type; выбранный пункт: `set_point` пишет в сессию
  код/адрес, рендер подставляет адрес пункта в title/description.

## 2. Производительность чекаута (метод: прямые POST index.php?route=checkout/simplecheckout с телом формы, simple_ajax=1)

| сценарий | 1-й запрос | 2-й |
|---|---|---|
| без котировок (страна не выбрана) | 1.2–1.6с | 1.3с |
| СПб, страна RU, котировки | **8.4с** | 1.3с |
| Москва, страна RU, котировки | **4.3с** | 1.6с |

- Кэш ApiShip: `setData/getData` библиотеки — `$_SESSION['shipping_apiship']`,
  TTL 10 минут; кэшируются `apiship_data()` (lists/points по фильтру города,
  providers, statuses, connections) и калькулятор (хэш аргументов вкл. корзину).
  Каждая новая сессия / смена города / 10 минут бездействия = холодный прогрев
  последовательными HTTP-вызовами ApiShip (curl TIMEOUT 20с; пункты постранично
  по limit=10000).
- «Раньше было быстрее» — совпадает с попаданием в тёплый кэш либо быстрым ответом
  ApiShip; архитектурно каждый новый посетитель всегда платил холодный прогрев.

## 3. Адрес пункта 5Пост (live, сессия с городом СПб)

- `get_points`: 5Пост(x5) 605 пунктов (6 с пустым address), Яндекс(yataxi) 799,
  у обоих поля address заполнены; постамат 5Пост пример: «Санкт-Петербург,
  пр-кт Индустриальный, д.30 корпус к. 23, офис 23», тип «Постамат», tariff
  «Стандартный тариф до постамата».
- `set_point` для постамата 5Пост и пункта Яндекса: title с адресом, address1
  с адресом, «сменить ПВЗ» — оба ОК.
- Перерендер чекаута с выбранным постаматом 5Пост: label = «Самовывоз из Постамата
  5Post OM122851 Санкт-Петербург, пр-кт Индустриальный, … 224р. сменить ПВЗ» —
  адрес ЕСТЬ. Вывод: «адреса нет» у заказчика = состояние до выбора пункта
  (заказ #6728 прошёл без пункта).
- Нюанс разметки: в `set_point` title строится из сырого `$point['address']`, в
  рендере котировок — из собранного `get_address($point)` (структурированные поля);
  на практике оба дают адрес, рассинхрон не проявился.

## 4. Курьер без адреса

- Поля Simple (`shipping_address[address_1]`, `customer[email]`) не имеют маркеров
  обязательности — серверная валидация Simple на этих полях не настроена.
- Курьерские методы: коды `apiship.door_*`; при наложенном платеже курьер скрыт
  (правило 1.14 — нал только ПВЗ), в тестах с налом рендерятся только 2 ПВЗ-метода.
