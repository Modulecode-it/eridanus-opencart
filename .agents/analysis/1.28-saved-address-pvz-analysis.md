# Анализ 1.28: ПВЗ Яндекса при сохранённом адресе

**Задача:** 1.28-saved-address-pvz
**Дата:** 2026-11-19 → дополнено 2026-11-20
**Статус:** переоткрыта 20.11 — найдена первопричина (не кеш)

## ФИНАЛЬНЫЙ ДИАГНОЗ (20.11, доказан прямым экспериментом с ApiShip)

**Улица (ext_address) в addressString расчёта урезает список ПВЗ до «ближайших
к дому» (8–11 точек), без улицы агрегатор возвращает все точки города (664/836).**

Прямой прогон `POST https://api.apiship.ru/v1/calculator` (dev-токен, Единорог
300 г, 19×15×3; probe: `agent-tmp/apiship_calc_probe.py`):

| addressString | x5 pointIds | yataxi pointIds |
|---|---|---|
| регион + город + **улица** | **8** | **11** |
| регион + город (без улицы) | 664 | 836 |
| только город | 664 | 836 |
| город + улица | **8** | **8** |

Механика: ApiShip геокодирует адрес до дома и режет `tariff.pointIds` до зоны
дома. Если рядом с домом точек провайдера нет (у клиента улица «Авиа-18/3-91») —
pointIds пустеют и метод «Самовывоз Яндекс.Доставка» пропадает из списка
целиком → симптом клиента 1:1.

## Цепочка на сайте (кто передаёт улицу)

- При выборе **сохранённого адреса** Simple кладёт `address_1` из БД в сессию
  (подтверждено POST-перехватом: `shipping_address[address_1]=«Тестовая ул…»`,
  `postcode=''`) → `get_quote_list` (модель:265) передаёт её как `ext_address`
  в `apiship_calculator` → попадает в `to.addressString` (библиотека:448).
- При **«новом адресе»** поле улицы для ПВЗ-методов скрыто (набор полей 1.10) и
  не отправляется → расчёт по городу → полный список.

Живые прогоны прода (TEST-клиент, Единорог×1, одна сессия, 20.11):
сохранённый адрес → 8/11 точек; «новый адрес» (без улицы) → 606/823; смена
оплаты/индекса эффекта не даёт (индекс в калькуляторе принудительно
обнуляется: библиотека:363 `$postcode='';` — в хэш кеша тоже не входит).

## Отвергнутые гипотезы

- Зона в сохранённом адресе (у клиента zone_id=106 СПб — корректна).
- Индекс (выкидывается из расчёта; 190000/197373/без — не влияет).
- Оплата codCost (нал/карта — точки одинаковы).
- Кеш (1.27) — не первопричина: различие воспроизводится свежим расчётом
  каждый раз; кеш лишь закреплял урезанный вариант на 300с.
- «Мало точек у Яндекса — норма» — неверно: в СПб у Яндекса 823 ПВЗ.

## Кандидат фикса (не реализован, ждёт решения Максима)

В `catalog/model/extension/shipping/apiship.php` (`get_quote_list`) не
передавать `ext_address` в `apiship_calculator` (считать по городу):
- ПВЗ всегда полный список города; кейс клиента «метод пропал» исчезает;
- door-тариф считается по городу (доставка до подъезда по дому всё равно не
  тарифицируется — подъезд/этаж не передаются; проверено probe: deliveryToDoor
  есть у x5/yataxi и без улицы);
- цена не меняется (тарифы двери от города), время расчёта не растёт.

Альтернатива (дороже): отдельный расчёт door-тарифа с улицей — ×2 запроса к
агрегатору, отклонено.

## Хронология расследования

1. 19.11: А/Б dev (5 сценариев) и прод (А/Б + карта) — метод «Яндекс ПВЗ»
   присутствовал в обоих сценариях; сделан вывод «кеш 1.25-эпохи, закрыто».
   НЕВЕРНО: сравнивалось наличие метода, не число точек.
2. 20.11: вопрос Максима «мало точек» → консоль-скрипт (get_points) показал у
   Максима 606/823 (новый адрес) против 7/11 у агента (сохранённый) →
   систематика: сохранённый=урезано, новый=полный; исключены индекс/оплата/
   улица-как-таковая (тест «новый адрес с улицей» дал полные списки — улица
   тогда не долетела в сессию расчёта); POST-перехват показал: улица уходит
   только при сохранённом адресе.
3. Прямой probe калькулятора ApiShip ×4 комбинации — **улица в addressString
   урезает pointIds** — первопричина. Эксперименты: временное включение
   debug-режима модуля на проде (выключен обратно, режим normal подтверждён),
   probe с dev-токеном (токен из скрипта удалён, плейсхолдер).
