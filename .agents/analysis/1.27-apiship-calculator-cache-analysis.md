# Анализ 1.27 — кеш калькулятора ApiShip: пустые/урезанные ответы

**Задача:** 1.27-apiship-calculator-cache
**Дата:** 2026-11-18
**Статус:** завершён

## Текущее Поведение (до правки)

`system/library/apiship/apiship.php`, `apiship_calculator()`:

1. Ответ без `body.errors` безусловно кладётся в общий файловый кеш `sharedCacheSet('apiship_calculator', $data_hash, $data, 1800)` (строка ~482). «Без ошибок» ≠ «полный»: агрегатор не помечает частичные ответы.
2. Хэш = md5(страна+регион+город+индекс+адрес+провайдеры+`print_r($products)`+сумма+нал+extraParams) → у каждой корзины своя запись: урезанный ответ для «Единорога» не лечится повторными попытками 30 минут (диагноз 1.25-сессии-3).
3. **Пустой ответ тоже кешируется:** при сбое curl `curl_exec` возвращает `false` → `json_decode(false)` = `null` → `isset($data['body']['errors'])` = false → null-body уходит в кеш на 1800с. Живой кейс пойман в верификации 1.26 («Единорог×1+СПб+карта» — пусто на dev и прод одновременно; `get_last_tracing_id` без ID).
4. Ошибочные ответы (`body.errors`) не кешируются — эта ветка уже корректна.
5. Ветка чтения `sharedCacheGet(..., 1800)`: третий аргумент в теле функции не используется (TTL зашит в запись при записи) — параметр декоративный.

## Вызывающие (downstream)

`catalog/model/extension/shipping/apiship.php`: 4 вызова (`getQuotes` ~265, ~964, ~1176, заказ ~1918) — все берут `['body']` и обходят `deliveryToPoint`/`deliveryToDoor` через isset-гарды; провайдер без `tariffs` игнорируется. `null`-body безопасно даёт пустой список котировок. Правки модели не требуются — фикс самодостаточен в библиотеке.

## Эвристика «плохого» ответа

Честного признака урезанности ApiShip не возвращает. Счёт тарифов по типам (зеркалит семантику модели):

- **0 + 0** (нет тарифов ни в одном типе; сюда же null-body) — транзиентный сбой или нераспознанный адрес → не кешировать вовсе.
- **>0 + 0 или 0 + >0** (асимметрия) — двусмысленно: честное покрытие региона (Псков: только 5Post-ПВЗ; ЛО: курьер без ПВЗ Яндекса) либо урезанный ответ → короткий TTL 120с, лог-маркер.
- **>0 + >0** (полный по типам) — базовый TTL, но сокращен 1800→300с: главный кейс HAR 1.25 (yataxi исчез из `deliveryToPoint` при живом `deliveryToDoor`) симметрию не нарушает и эвристикой не ловится — его окно режет только общий TTL.

Теневой копии library в `system/storage/modification/` нет — рабочий файл исполняется напрямую.

## Риски и Решения

- **Больше запросов к калькулятору ApiShip** (TTL 300 вместо 1800, асимметричные регионы — 120): приемлемо — расчёт идёт на смену адреса/оплаты, не на каждый ребилд чекаута; КПУ — документированная плата за исчезновение 30-мин «пропаданий».
- **Ложные срабатывания эвристики на регионах с честной асимметрией** (Псков и т.п.): для них просто TTL 120с — отображение не меняется.
- **Переустановка/обновление модуля ApiShip вернёт вендор-файл** — потеряются и 1.23, и 1.27; при обновлении сверять файл (заметка и в implementation log).
- **Старые записи кеша** (записаны с TTL 1800 до деплоя) протухнут сами ≤30 мин после деплоя; принудительная чистка `system/storage/cache/apiship.*.cache` опциональна.

## Результаты Анализа

Фикс локализован в одном месте (`apiship_calculator`), downstream не затронут, эвристика и TTL соответствуют кандидатам из 1.25-сессии-3 и рекомендации 1.26-final-report.
