## Текущее поведение (механизмы из кода)

### Поток котировок

`catalog/model/extension/shipping/apiship.php` → `get_quote_list($address)` →
`system/library/apiship/apiship.php` → `apiship_calculator($country, $region, $city, …)`:

- город+регион+улица собираются в строку `to.addressString` (индекс внутри калькулятора принудительно игнорируется: `$postcode = ''`, apiship.php:363); распознавание адреса выполняет сам ApiShip (нечёткое геокодирование);
- **наложка**: если выбранный способ оплаты входит в `shipping_apiship_cash_on_delivery_payment_methods` (на проде — `cod`, runbook 1.21 §6.5), в запрос добавляется `codCost` → ApiShip возвращает только тарифы, поддерживающие наложенный платёж. У Яндекса (yataxi) с `codCost` исчезает курьер (дверь), остаётся ПВЗ (проверено ещё в 1.14); у 5Post остаются постаматы;
- общий файловый кэш калькулятора 30 мин (правка 1.23), `data_hash` включает город и `cash_on_delivery` — кэш COD/карты и разных городов не смешивается;
- пустой город → ранний выход с message «Необходимо выбрать город»; при нераспознанном городе API отдаёт `errors` → message «Нет доставок для города %s» (показывается как метод-заглушка только при включённой `shipping_apiship_error_stub_show`).

### Рендер списка ПВЗ в Simple

В `get_quote_list` режим «все ПВЗ на одной карте» (`shipping_apiship_group_points=1`):
первый цикл ищет совпадение с `shipping_apiship_last_select_code` (последний выбранный пункт в сессии, apiship.php:358-434) и выводит **ровно один метод** (последний выбранный пункт) с `break`; если выбора не было — тоже один метод (самый дешёвый, второй цикл с `break`). ПВЗ обоих провайдеров доступны на общей карте («смотреть ПВЗ»). Режим «для каждой СД своя карта» — по методу на провайдера.

Курьерские методы (`deliveryToDoor`) добавляются отдельным блоком независимо от группировки.

Выводы:

- **Опечатка в городе** не ломает чекаут: ApiShip распознаёт город нечётко (тест 4). Если город нераспознаваем — методы Яндекса пропадают, остаётся 5Post (тест 5; видимо, x5 резолвится по региону/индексу), сообщение об ошибке не показывается. - **«Яндекс пропал» на скриншоте 2** = суперпозиция штатных механизмов (все подтверждены на проде, см. ниже): (а) выбрана «Оплата при доставке» → `codCost` в калькулятор → курьер Яндекса скрыт (нал = только ПВЗ, решение 1.14); (б) **состав корзины определяет наличие провайдера в списке** — ApiShip не возвращает тариф провайдера, если корзина не проходит его лимиты (вес/габариты): у заказчика «боевой» заказ — для него Яндекс-тарифов не вернулось, остался 5Post (постамат OM1267633 «помнится» из тестового заказа той же сессии — рендер с адресом пункта и «смотреть ПВЗ»); (в) при переключении оплаты на карту курьер возвращается, если корзина проходит лимиты.

## Риски / решения

- Поведение «нал скрывает курьера Яндекса» может выглядеть как «пропала доставка» (что и произошло). Решение: пояснение заказчику + возможный UX-текст «Курьер недоступен при оплате при доставке» — этап 2 (2.1).
- Список методов зависит от корзины (лимиты провайдеров) — покупатель с крупным заказом может лишиться 5Post или Яндекса без объяснения. Возможный UX: показывать недоступные методы серым с причиной; решение — этап 2.
- Нераспознанный город не даёт видимой ошибки (заглушка `shipping_apiship_error_stub_show` выключена). Системно закрывается этапом 2 (2.1: регион/город с автодополнением из справочника).
- Уточнение к ранней гипотезе: прод и dev оба в режиме «у каждой СД своя карта» (`group_points=0`); «один метод» на скриншоте — не группировка, а отсутствие Яндекс-тарифов для корзины заказчика + сессионный выбранный пункт.


## Методика (live-тест через HTTP, без браузера)

Сессия curl + cookie; товар в корзину `route=checkout/cart/add`; пересчёт чекаута — POST `route=checkout/simplecheckout` c `simple_ajax=1` и полным набором полей формы (guest). **Грабли:** curl из Git Bash на Windows отправлял кириллицу не в UTF-8 — Simple молча отбрасывал `city`/`address_1` (остальные поля проходили), из-за чего блок доставки был пуст. Фикс: тело запроса генерировать python-скриптом в UTF-8 (`urllib.parse.urlencode`) и слать `--data-binary @file`. Заказы не оформлялись.

Браузерный плагин (browser-use / node_repl MCP) в этой сессии недоступен (инструмент не подключён к модели) — проверка сделана HTTP-методом, результаты эквивалентны для витрины.
