**Задача:** 1.11-product-page-widget-alert
**Дата:** 2026-09-08
**Статус:** завершена

## Запрос

1. На карточке товара появился блок «Выберите вариант доставки» — убрать.
2. При клике «Купить» всплывает окно с «error» и HTML — найти причину.

## Разбор и решения

### 1) Блок «Выберите вариант доставки»

- Источник — сторонний модуль **«</> Shipping Widget — расчет доставки на любой
  странице»** (`ll_shipping_widget`, автор p0v1n0m, v2.2.4): рисует калькулятор
  доставки на карточке (город/страна + расчёт), позиционируется у кнопок покупки
  (настройка «Переместить» = CSS-селектор).
- Отключено: статус модуля → «Отключено». Особенность: у модуля самозащита —
  сохранение настроек требует валидное поле `module_ll_shipping_widget_license`
  (HMAC-SHA256 от HTTP_HOST+код модуля), иначе ветка «no license» вызывает
  uninstall (и фаталит 500). Лицензия вычислена, форма отправлена штатно (302,
  «успешно»).
- Проверка: `curl` карточки — вхождений «Выберите вариант доставки» /
  `ll_shipping_widget` — 0. Блок исчез.

### 2) Окно «error + HTML» при «Купить»

- Обработчик в `catalog/view/theme/default/template/product/product.twig`
  (бывшие строки 426–428): при ошибке AJAX `checkout/cart/add` показывал
  `alert(thrownError + statusText + responseText)` — то есть «error» + ВЕСЬ HTML
  страницы-ответа. Это и есть увиденное окно.
- Почему AJAX падал: `cart/add` в момент обращения возвращал HTML-страницу
  ошибки вместо JSON (транзиентное состояние сервера — период моих сохранений
  настроек и рестартов контейнера). Сейчас `POST cart/add` отвечает корректным
  JSON `{"success":…}` (проверено curl'ом).
- Фикс (код, ждёт деплой): обработчик заменён на `console.error` (полная
  диагностика в консоли) + дружелюбный alert «Не удалось добавить товар…
  обновите страницу». Без вывода сырого HTML пользователю.

- Коммит `b792c2d` запушен и вытянут на сервер (`git pull` после разрешения
  конфликтов .agents через stash + бекап дубликатов в /tmp).
- Нюанс: правки не появились на витрине сразу — страницы отдавались из теневых

  Выполнено «Обновить» модификаторов (`marketplace/modification/refresh`) +
  очистка кэша темы (`common/developer/theme`) через HTTP-админку.

  обработчика «Купить» присутствует; `ll_shipping_widget` отсутствует;

- На сервере остался хвост: массовый «M»-статус из-за CRLF/LF (см. инструкцию

## Дополнение 2026-09-18: истинная причина окна при «Купить»

После деплоя пользователь сообщил, что окно при «Купить» осталось. Расследование:

- Диалог содержал «error» + HTML и принадлежал НЕ обработчику product.twig
  (он уже был заменён на дружелюбный), а скрипту из OCMOD **id=64
  «Yandex.Metrica» (opencart.ru)**: его патч в footer подмешивал
  `sendDataForEcommerceYandexMetrica()` и переопределял `cart.add` — каждый
  клик «Купить» сначала дёргал `route=product/product/getProductDataForYandexMetrica`.
- Эндпоинт **404** (контроллерный патч мода не применился — метода нет) →
  error-обработчик скрипта показывал alert с дампом HTML.
- Счётчика Метрики на сайте не настроено вовсе (`mc.yandex.ru` на страницах —
  0 вхождений), т.е. e-commerce скрипт работал «в никуда» с первого дня.

Действия:

1. Отключён модификатор id=64 (`marketplace/modification/disable`), обновлены
   модификаторы (refresh).
2. Проверено на живой странице товара: `sendDataForEcommerceYandexMetrica` —
   отсутствует; старый дамп-обработчик от метрики — отсутствует; остался один
   `alert(thrownError` только в обработчике загрузки файлов опций (на товарах
   без файловых опций не срабатывает); мой дружелюбный обработчик — на месте;
   `fonts.googleapis` — 0. Главная и чекаут — 200.
3. Примечание для пользователя: открытую вкладку товара нужно обновить (F5) —
   в памяти старой вкладки оставался старый скрипт.

Восстановление e-commerce Метрики (если понадобится): включить мод 64 и
починить применение его контроллерного патча (или реализовать
`getProductDataForYandexMetrica` нативно, убрав патч) + настроить сам счётчик
(Аналитика → Яндекс.Метрика).
