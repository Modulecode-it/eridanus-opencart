# 1.14 — Восстановление OCMOD-теней ApiShip + тестирование чекаута

Дата: 2026-09-19. Статус: тени восстановлены и запушены (`c87a48a`, `1123a0a`); ждём `git pull` на сервере для активации; после — тест ПВЗ-карты и тест-заказ.

## Что случилось (диагноз)

При тестировании ПВЗ-флоу после редизайна 1.13 выяснилось: на странице `checkout/simplecheckout` отсутствуют функция `apiship_open` и класс `ApishipMap` — скрипт модуля ApiShip вообще не попадает на страницу, ссылки «выбрать ПВЗ» нет.

Причина: интеграция ApiShip с Simple выполняется OCMOD-модификатором (`apiship-1.2_3.x.ocmod/install.xml`), который патчит `simplecheckout_shipping.php/.twig`, стандартный `shipping_method.php/.twig` и админ-заказы (`sale/order.php`, `order_form`, `order_info`, `order_list`). Эти тени НЕ были в git: правило `.gitignore` `system/storage/modification/**` (новые файлы требуют `git add -f`). Зачистка `git clean -fdx system/storage/modification/` в задаче 1.12 удалила их с сервера как игнорируемые. При этом гит-тень `order_info.twig` существовала, но БЕЗ апишип-патчей (0 упоминаний) — т.е. админ-интеграция ApiShip (экспорт/ярлыки/накладные из карточки заказа) тоже молча отвалилась.

## Что сделано

1. Написан одноразовый парсер `install.xml` (семантика OCMOD: `search`+`before/after/replace`, `trim`, `index`, `error=skip`) — собрал 7 теней из текущих git-оригиналов + патчей:
   - `catalog/controller/checkout/simplecheckout_shipping.php` (валидация «выберите ПВЗ»; поверх хотфикса 22039ff);
   - `catalog/view/theme/default/template/checkout/simplecheckout_shipping.twig` (вывод `script`, логотип и ссылка «выбрать ПВЗ» у ПВЗ-метода);
   - `catalog/controller/checkout/shipping_method.php` + `.../checkout/shipping_method.twig` (стандартный чекаут);
   - `admin/controller/sale/order.php`, `admin/view/template/sale/order_form.twig`, `order_list.twig` (+ пересобран `order_info.twig` с учётом `index="1"`).
   Примечание: операция с якорем `//--></script></div>` в order_form находится node-поиском (grep в bash её не видел) — применена, как и оригинальным OCMOD.
2. Закоммичено (`c87a48a` — пересборка order_info; `1123a0a` — остальные 7 через `git add -f` по правилу .gitignore), запушено. На сервере требуется `git pull`.
3. Восстановлен ПВЗ-набор полей Simple: `checkout[0].shippingAddress.rows['apiship.point*|']` = `address_id, firstname, lastname, country_id, zone_id, city` (клон default без postcode/address_1) — через Vuex `SAVE_SETTINGS`, сервер подтвердил. Проверено вживую: при выборе «Самовывоз Яндекс.Доставка» поля Индекс/Адрес скрываются, при «Курьере» — возвращаются.
4. Установлен `shipping_apiship_description_point_template` = `%link` (был пуст — дефолт модуля; ссылка «выбрать ПВЗ» в Simple не выводилась вовсе). После активации теней ссылка будет рендериться и OCMOD-патчем — шаблон описания следует вернуть в `''`, чтобы не задваивалась.

## Важные находки (ApiShip-калькулятор)

- Настройка `shipping_apiship_cash_on_delivery_payment_methods` ПУСТА → модуль никогда не шлёт `codCost` → котировки не зависят от способа оплаты, и заказ с «Оплатой при доставке» уйдёт в ApiShip БЕЗ суммы наложки. Прямой тест: с `codCost` у Яндекса остаётся только тариф до ПВЗ (дверь исчезает). Решение на выбор владельца: включить `cod` в списке (наложка останется только для ПВЗ — корректно) или убрать «Оплату при доставке».
- Калькулятор ApiShip чувствителен к адресной строке: несовпадение регион/город (напр. «Ленинградская область» + г. СПб) убирает курьерский тариф; отдельные улицы геокодятся нестабильно (Казанская — пусто). Кэш калькулятора живёт в PHP-сессии вечно (по хэшу адреса) — «плохой» ответ залипает до смены адреса/сессии.
- В течение дня с IP dev-сервера ответы деградировали (курьер пропадал при валидном адресе), при том что локальные запросы в ту же минуту возвращали оба тарифа — похоже на лимиты ApiShip по IP/токену от моего объёма тестов. Для реальных покупателей (1-3 запроса) нехарактерно; при повторении — вопрос в поддержку ApiShip с `x-tracing-id` (модуль хранит последний: `shipping_apiship_last_tracing_id`).
